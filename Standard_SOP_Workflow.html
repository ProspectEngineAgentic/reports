1. The Standing Formula

The agency runs on ONE repeatable formula so the CEO does not re-instruct each session. On session start: read WORKFLOW.md + clients.json, sync WhatsApp (the shared sync script), then run DAILY_ROUTINE.md for every client whose work is due. For each active client, every working day:

  1. Listen. Sync WhatsApp and read the client's group. Read the latest messages BEFORE drafting any outreach so we use the client's current situation, not stale facts.
  2. Reply in voice. 7th-grade English, NO dashes, human, warm, polite, like an expert provider who owns the company. If a message needs a real decision you cannot make, draft it and flag the CEO instead of sending.
  3. Refine on feedback. Update and perfect shared work, reconfirm before live. Treat their edits as gold.
  4. Do the SOP. Run that client's daily SOP from their OPERATING_PLAN.md. Respect quotas, live-inbox checks, single-instance rules. Never mix two clients.
  5. Content one batch ahead. Draft the next batch of posts + matching 4K visuals with a FRESH structure each batch. Share review HTML for approval. On approval, schedule one per day at the client's local 10:00.
  6. Engage. Check + reply to comments on published posts; run the post-publish boost + engagement comment; run network engagement where defined.
  7. Update the client TODO ([CLIENT_FOLDER]\reports\CLIENT_TODO.md).
  8. Commit to git after every task. No exceptions. Add-only, never mix clients.
  9. Learn. Append to the client's OPERATING_PLAN.md Optimisation log.
Timezone rule: publish at each client's LOCAL 10:00. The agency PC clock differs from client local time, so each client's publish task fires at the pc_fire_time in clients.json. Recheck PC fire times at every DST change.

2. Orchestration Model

  • Main coordinator (Claude session): reads WORKFLOW.md + clients.json, runs the daily routine for each due client, then summarizes per client.
  • Subagents (Task tool): fan out independent per-client research/audits in parallel. ONE agent per client so work never crosses. Subagents are read-only / draft-only; sends stay gated.
  • STOP GATE on every send-capable subagent: killing the python child does NOT stop a subagent's watch loop. Add an explicit STOP GATE, rename the drafts file aside on pause, use TaskStop + SendMessage together.
  • Windows Task Scheduler (always on): runs all script-only automation without a Claude session — the backbone (see Section 9).
  • Skills / hooks / cloud routines: schedule creates recurring routines; update-config adds settings.json hooks/permissions. Cloud routines must use the API-fetch pattern (embedded token from ops config), NOT git_repository sources, which auto-disable when the work repo is not connected to the Claude Code GitHub app.
  • Single sending instance per account. Never run two sending scripts against one account at once (LinkedIn 429). Verify exactly one instance after launch. Never pipe a sending script to Tee-Object via the Bash tool.
  • Never mix clients. Each client has its own local folder, git folder, account, and trackers.

3. Global Standing Rules / Guardrails

Non-negotiable. Apply to every client.

Messaging voice

  • 7th-grade English. NO em dashes / hyphens in client-facing copy. Match the client's language variant.
  • Human, like texting a friend. Banned AI filler: "outbound", "GTM", "signal", "leverage", "happy to", "I would love to", "trade notes", "if it is ever useful", "no agenda, just a good chat". Read aloud first.
  • Comment voice: no generic AI openers ("Spot on", "100%", "This rings true"); specific lived detail per author; cover the whole argument; 7th grade; no dashes.

No-sell, convert to a call

  • Act as the client (first person). The goal of a prospect message is to BOOK A SHORT CALL, not sell. Share the [client calendar link] and invite a short, no-pressure call. Never pitch service / packages / price — the client closes live on the call.
  • Decline = door-open courtesy note, then stop. Skip any optional add-on offer for experts in that domain.

Never contact anyone already in contact with the client

  • Never nurture/engage/DM/like/comment anyone already in contact on ANY channel, or whom the client said to drop. Scan each contact's live thread; any inbound = "in contact" = remove. The "recent" check is not enough.
  • Don't just delete — park them with full info in [CLIENT_FOLDER]\data\do_not_touch_contacts.json + excluded_contacts_tracking.json + a readable <Client>_excluded_contacts.md. Replicate per client.

Do-not-contact lists (per client)

Maintain a per-client DNC list (companies, subsidiaries, named people, red-marked profiles, coordinate-first targets). Canonical [CLIENT_FOLDER]\data\<client>_dnc.json; enforce in that client's invite + engagement scripts. Coordinate-first targets need CEO sign-off before any touch.

BLOCKED accounts

A global BLOCKED-accounts list is maintained in ops config (actual names / IDs live there, not in this shared doc). No messaging, invites, comments, reactions, posting, or engagement of any kind from a blocked account, for any client, ever. Check the list before assigning any sending account.

Verify before send

Strictly verify job title, company, persona on the LIVE profile before any outreach. Use a role-fit filter that skips off-persona / career-drifted prospects at send time where accuracy beats volume.

Live-inbox check + stop-on-reply (the #1 invariant)

Before EVERY M1/M2/M3 (or any send), GET the live thread, read the full conversation, confirm the newest message is theirs. Never trust the tracker alone. Any reply = stop that sequence FOREVER. "Send all" does NOT override this.

Only reply to campaign / target persona

Inbox replies ONLY to people in the active campaign or matching the client's ICP. Investors, recruiters, vendor pitches, off-target inbound go to the CEO as info only.

Approval before anything client-facing

  • Never publish to a client's live profile without approval. Do all tasks in sequence (no "skip" options), share the deliverable for CEO review first; he confirms + sends, then proceed.
  • Never name Claude/AI tooling to a client without CEO permission, even if the client raises it first. Ask for "your ideas", not "Claude's ideas".

Browser-openable deliverables

Share reports/content as HTML/links, NEVER a flat PNG. Flow: publish HTML to the reports/Pages repo (named in ops config) → the public Pages URL → review in the Operations Team group → CEO shares the link in the client group.

Notify Operations Team after every publish

After ANY LinkedIn post from a client profile, share the post link in the "Operations Team" WhatsApp group and ask the team to interact. Use the shared notify helper; bake into each client's publisher.

Commit to git after each task

Add-only. Never mix clients. NEVER run git sparse-checkout set <new-folder> on the work repo (destructively deletes files). Before committing, confirm git diff --cached --name-status shows zero D. Use git read-tree HEAD + git add <target>.

Technical hygiene

  • Never use python -c inline on Windows — write a .py file and run python "path.py".
  • Never probe with real endpoints. POST /posts is permanent (no DELETE for self-posts). Read docs or ask first. Correct repost field is repost: <post_id> + text: <caption>.
  • Fix the command, not just the symptom: every error needs TWO fixes — recover the damage AND patch the script/config so it cannot recur, then commit.
  • Don't pattern-match vendor API error names to causes; run the experiment that changes the suspected variable first.
  • Research → weigh 3-4 options → pick best → self-check before delivering.

Unipile ID + invite rules (generic)

  • Resolve the real provider_id via GET /users/{ACw}?account_id=SENDER_ID before invite/messaging. The ACw→ACo char-swap is unreliable; raw ACw returns a misleading 403 feature_not_subscribed.
  • cannot_resend_yet = with-note weekly cap AND an account-wide burst cap (~25/day → multi-day lock). Send invites WITHOUT a note; personalize via DM after accept.
  • already_connected is ambiguous (fires for pending invites too) — use /users/relations as truth.
  • Rate limits: LinkedIn caps ~80-100 invites/day/account; failed requests still count. On 429, stop for the day, wait 2-3 hrs. disconnected_account = session expired → refresh cookies in the Unipile dashboard.

Reactions / boost rules

  • Boost reactions are a CONTEXTUAL MIXED-TYPE set (like / insightful / support / celebrate / love), never all-like. ~15 per post. Comment rotation: never repeat the same profile day-to-day; client principals occasional (max 1/post, max 2 days/week); cleared local commenter accounts rotate LRU; 5-6 comments/post.
  • Every comment must also fire a like from the same account (comment alone reads transactional).

Prospect timezone rule

All outbound activity sends in the PROSPECT'S local Mon-Fri 9-18. Use the shared timezone util.

Shared credentials

Unipile API key, base URL, GitHub token, and any other secret are stored in ops config / CLAUDE.md, never in shared docs. Never paste a key, token, account ID, chat ID, or calendar link into a hosted or shared file.

4. Per-Client SOP Structure

Every client gets its own OPERATING_PLAN.md built from this standard. Do NOT keep client identity in this shared doc. Each plan should cover:

  • Identity & channels: company, contact, channel(s), timezone, local post time + PC fire time, the client's account, WhatsApp chat, git folder, local folder (values in clients.json / ops config).
  • Voice & content rules: language variant, tone, extra banned phrases, visual style, comment-reply posture.
  • ICP / personas + CTA rules: who to target, who NOT to, current campaign CTA.
  • Workstreams: outreach, content, any specialised nurture/sourcing track. Keep separate campaigns separate.
  • Sequence + caps: weekly invite cap (week-to-date), daily volume, M1/M2/M3(/M4/M5).
  • Do-not-contact notes, data files, watch scope, standing context + blockers.
Watch scope rule: autonomous action only for clients explicitly cleared for it; all other active clients are monitor-only (act only on CEO command). Any client whose account is on the global BLOCKED list is monitor-only and that account is never used.

5. Outreach Sequence Pattern

Defaults for any new client (tune per client in OPERATING_PLAN.md):

StageDefault timing
InviteSilent connect (no note) where with-note is unavailable; personalize via M1 after accept
M11 day after connect (or immediately on detecting a new connection)
M2+4 days after M1 (if no reply)
M3+10 days after M2 (if no reply)
M4 / M5Only where a longer sequence is defined; widen gaps (e.g. +5d, +7d)
  • Daily invite volume: typically ~26-30 per account, ~5 min apart.
  • Weekly invite cap: set per account, typically ~150-205/week (Mon-Sun), NOT a hard daily number. Always count week-to-date from that client's invitation_log.json at session start and send only the remainder.
  • No-connect-step personas (DM-first) use a different cadence (e.g. M1→M2 ≥3d, M2→M3 ≥5d) — define per client.
Universal (every send, every client): live-inbox check before EVERY send; any reply = stop forever; single sending instance per account; prospect local Mon-Fri 9-18; verify profile/persona on the live profile first; DNC + global BLOCKED list enforced.

6. Content + Engagement Cycle

  • Batch-ahead drafting: keep every client one batch ahead. Posts are top-voice, 7th-grade, no dashes, strong standalone hook, one takeaway + one question, soft CTA, hashtags at end, 100% sourced. Default batch ~5 posts; company-page cadence set per client.
  • Fresh visuals: 4K visuals built HTML → headless Chrome; vary structure every batch; never the same template two posts running; carousels/data charts perform best; brand-safe photos only. Some clients want TEXT-led visuals only — honour their preference.
  • Approval gate: share the review HTML to the client's WhatsApp (after CEO review). Publish only on client approval AND the queue gate (enabled:true + per-post approved:true + due-today).
  • Daily publish at local 10:00: each client's publisher fires at its pc_fire_time from clients.json.
  • Post-publish engagement (baked in): ~15 mixed-type boost reactions + exactly ONE engagement comment from the cleared commenting account (auto-likes). Then notify the Operations Team WhatsApp group with the post link. Dedup via the shared engaged-state file.
  • Comment-watch + reply (STANDING, daily): check comments on every published post and reply in voice (as the person on profile posts, as the page on company posts). Concede the point, restate ours softly, no hard CTA to peers, no generic openers.
  • Network-post engagement: each new post from any cleared (non-blocked) network account gets ~15 boost reactions + 1 personal comment (not rotation). Comment non-negotiables: no phrase lifting, identical operator voice, well-researched, no restating the thesis, cover the whole argument, grade-7; if outside the lens with no honest parallel, like the post, don't comment. Dedupe before send (fail-closed). Always like + comment, never comment alone.
  • Company-page follow-invites: monthly per client via the raw passthrough POST /linkedin → voyagerRelationshipsDashInvitations (~250/mo).

7. Nurture Motion (cold dormant re-warm)

Enable per client as the campaign matures. SOP at [CLIENT_FOLDER]\reports\<Client>_NURTURE_SOP.md; tool runs DRY RUN by default, --send only after CEO approval.

  1. Build the list from tracker + live inbox: OLD ghosted leads who once had a real conversation (sent M1/M2/M3, never replied) tagged DORMANT_NURTURE.
  2. Exclude anyone already in contact on ANY channel (scan last-msg-inbound, not just "recent"), plus anyone the client said to drop. Hard guard against the do-not-touch list; park excluded contacts with full info.
  3. Take the oldest 10-15, live-inbox check each, skip on any new reply or recent client activity.
  4. Draft the re-open in the client's voice tailored to the angle. Acknowledge them + share the [client calendar link] + invite a SHORT no-pressure call. Never sell. Like + comment on their latest post the same day.
  5. Drafts go to the CEO before sending. Cap ~12/day, ~5 min apart, prospect local working hours. The client handles warm replies.

Runs automatically via the client's "Nurture" task. Nurture responders become live threads → route to the client, never auto-touch.

8. Monitoring

  • WhatsApp Watch (every 30 min, read-only): the shared watcher flags new/unanswered client messages; never sends. Autonomous action only for cleared clients; all others monitor-only. Reply only to genuine messages (skip reactions/OOO/thank-yous).
  • WhatsApp Daily Sync: refreshes the local WhatsApp store; a client-tagged subset mirrors to the work repo. --summary = read-only status.
  • Session-start read-latest: read the latest group messages BEFORE drafting any outreach.
  • Routine failure watcher: a cloud routine alerts the Ops WA group on any routine failure.

10. Escalation + Approval Flow

  • Needs CEO approval before going live: any client-facing message/post/report; any nurture --send; any new content batch; renew-or-churn decisions; touching coordinate-first DNC targets; any send for AT-RISK / unconfirmed clients.
  • Reports are shared as hosted HTML links, never flat PNGs: publish to the reports/Pages repo → the public Pages URL → review in the Operations Team group → CEO shares the link in the client group.
  • Off-target inbound (investors, recruiters, vendor pitches) → CEO as info only; never engaged by us.
  • Warm replies are the client's to close; route them to the client, never auto-touch.
  • After any publish: post the link to the Operations Team group asking the team to interact.

11. New-Client Onboarding Checklist

  1. Create the folder structure under [CLIENT_FOLDER]: data\, scripts\core\, scripts\archive\, content\, logs\, reports\, drafts\, creative\. Add a README.md.
  2. Create the git folder in the work repo using git read-tree HEAD + git add <target> (NEVER git sparse-checkout set).
  3. Add the client to clients.json: name, company, contact, status, channel, timezone, local_post_time, pc_fire_time, unipile_account, wa_chat_id, git_folder, local_folder.
  4. Set operating values: unipile_account (confirm NOT on the BLOCKED list), wa_chat_id, timezone, pc_fire_time (so local publish lands at 10:00; recheck at DST).
  5. Confirm with the CEO: ICP / personas, voice rules + language variant, scope (autonomous vs monitor-only), commercials/term, and the approval flow.
  6. Build OPERATING_PLAN.md from this standard (Section 4 structure).
  7. Set up lead DB + trackers: lead DB in data\, plus tracker.json, invitation_log.json, urn_map.json, <client>_dnc.json, and the do-not-touch / excluded-contacts pair.
  8. Set up the standard Windows tasks (Section 9) at the client's pc_fire_time; confirm the shared WhatsApp Sync + 30-min Watch cover the new chat id.
  9. Confirm the approval flow is live: review HTML to Ops group → CEO → client group; no client-facing action without approval.
  10. First batch: draft first content batch + visuals, share for approval, queue, then enable the publisher. Commit everything to git.
