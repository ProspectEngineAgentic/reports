1. The Standing Formula (daily per-client loop)

The agency runs on ONE repeatable formula so the CEO does not have to re-instruct each session.

On session start: read WORKFLOW.md + clients.json, sync WhatsApp (wa_daily.py), then run

DAILY_ROUTINE.md for every client whose work is due. For each active client, every working day:

  1. Listen. Sync WhatsApp and read the client's group (chat_id in clients.json). Read the latest

messages BEFORE drafting any outreach so we use the client's current situation, not stale facts.

  1. Reply in voice. Answer the client on their WhatsApp group: 7th-grade English, NO dashes, human,

warm, polite, like an expert provider who owns the company. If a message needs a real decision I

cannot make, draft it and flag the CEO instead of sending.

  1. Refine on feedback. If the client gave feedback on shared work, update and perfect it, then

reconfirm before it goes live. Treat their edits as gold.

  1. Do the SOP. Run that client's daily SOP from their OPERATING_PLAN.md (outreach sends, follow-ups,

content). Respect quotas, live-inbox checks, single-instance rules. Never mix two clients.

  1. Content one batch ahead. Draft the next batch of posts (top-voice, 7th-grade, no dashes, strong

hook, one takeaway, soft CTA) + matching 4K visuals with a FRESH structure each batch. Share the review

HTML to the client's WhatsApp group for approval. On approval, schedule one per day at the client's

local 10:00 via their publisher + Windows task.

  1. Engage. Check + reply to comments on published posts; run the post-publish boost + Saif comment;

run network/DV engagement where defined.

  1. Update the client TODO (Clients\<Client>\reports\CLIENT_TODO.md) with a short personality read.
  2. Commit to git after every task. No exceptions. Add-only, never mix clients.
  3. Learn. Note what worked, append to the client's OPERATING_PLAN.md Optimisation log, improve the

next batch and approach.

Timezone rule: publish at each client's LOCAL 10:00. This PC is UTC+6 (Asia/Dhaka). During European

summer (CEST) that local 10:00 is 14:00 PC. Each client's publish task fires at the pc_fire_time in

clients.json. Recheck PC fire times at every DST change (CEST is UTC+2, CET is UTC+1).

2. Orchestration Model

  • Main coordinator (Claude session): when the CEO opens the PC, reads WORKFLOW.md + clients.json,

runs the daily routine for each due client, then summarizes the day per client for the CEO.

  • Subagents (Task tool): fan out independent per-client research/audits in parallel. ONE agent per

client so work never crosses between clients. Subagents draft / read-only; sends stay gated.

  • STOP GATE on every send-capable subagent: killing the python child does NOT stop a subagent's watch

loop (it restarts from a filtered drafts file). Add an explicit STOP GATE, rename the drafts file aside

on pause, and use TaskStop + SendMessage together.

  • Windows Task Scheduler (always on): runs all script-only automation without a Claude session —

outreach sends, daily publish, WhatsApp sync, watchers. This is the backbone (see Section 9).

  • Skills / hooks / cloud routines: the schedule skill creates recurring remote routines;

update-config adds settings.json hooks/permissions for harness-executed automatic behaviours.

Cloud routines must use the API-fetch pattern (embedded GH token), NOT git_repository sources —

penclients is not connected to the Claude Code GitHub app, so git-source routines auto-disable.

  • Single sending instance per Unipile account. Never run two sending scripts against one account at

once (causes LinkedIn 429). Verify exactly one instance after launch. Never pipe a sending script to

Tee-Object via the Bash tool — the left side still launches and can double-fire.

  • Never mix clients. Each client has its own local folder, git folder, Unipile account, and trackers.

3. Global Standing Rules / Guardrails (non-negotiable)

Messaging voice

  • 7th-grade English, NO em dashes / hyphens in client-facing copy (reads as AI). British English for PDCA.
  • Human, like texting a friend. Banned AI filler: "outbound", "GTM", "signal", "leverage", "happy to",

"I would love to", "trade notes", "if it is ever useful", "no agenda, just a good chat". Read aloud

before sending.

  • Comment voice: no generic AI openers ("Spot on", "100%", "This rings true"); specific lived detail per

author; cover the whole argument; 7th grade; no dashes.

No-sell, convert to a call (prospect DMs)

  • Act as the client (first person, their voice). The goal of a prospect message is to BOOK A SHORT CALL,

not to sell. Share the calendar link and invite a short, no-pressure knowledge-sharing call. Never pitch

the service / packages / price in the text — the client closes live on the call.

  • PDCA/Robert calendar: https://calendly.com/robert-edward-pinnington-pdcaconsulting/30min.
  • Decline = door-open courtesy note, then stop. Skip the AI-automation offer for AI experts (acknowledge

+ courtesy only).

Never contact anyone already in contact with the client

  • Never nurture/engage/DM/like/comment anyone already in contact with the client on ANY channel, or whom

the client said to drop. Scan each contact's live thread; if the newest message is INBOUND (or any

inbound exists) they are "in contact" — remove them. The live-inbox "recent" check is not enough.

  • Don't just delete — park them in a separate tracking list with full info (PDCA:

data\do_not_touch_contacts.json + data\excluded_contacts_tracking.json +

reports\PDCA_excluded_contacts.md). Replicate this pattern for every client.

Live-inbox check + stop-on-reply (the #1 invariant)

  • Before EVERY M1/M2/M3 (or any send), GET the live thread, read the full conversation, and confirm the

newest message is theirs. Never trust the tracker alone. Any reply = stop that sequence FOREVER. "Send

all" does NOT override this. Duplicate sends have been flagged repeatedly; treat as the top invariant.

Only reply to campaign / target persona

  • Inbox replies ONLY to people in the active campaign or matching the client's ICP. Never engage

investors, recruiters, vendor pitches, or off-target inbound — those go to the CEO as info only.

Approval before anything client-facing

  • Never publish to a client's live profile without their approval. Do all assigned tasks in sequence (no

"skip" options), share the deliverable for CEO review first; he confirms + sends, then proceed.

  • Never name Claude/AI tooling to a client without CEO permission, even if the client raises it first.

Ask for "your ideas", not "Claude's ideas".

Use git read-tree HEAD + git add <target> instead.

Technical hygiene

  • Never use python -c inline on Windows — write a .py file and run python "path.py".
  • Never probe with real endpoints. POST /posts is permanent (Unipile has no DELETE for self-posts); a

"__probe_do_not_send__" was once published. Read docs or ask first. Correct repost field is

repost: <post_id> + text: <caption>.

  • Fix the command, not just the symptom: every error needs TWO fixes — recover the damage AND patch the

script/config so it cannot recur, then commit. Bake lessons into running code, not just memory.

  • Don't pattern-match vendor API error names to causes; run the experiment that changes the suspected

variable before recommending costly external action.

  • Research → weigh 3-4 options → pick best → self-check before delivering, so work is not bounced back.

Unipile ID + invite rules

  • Resolve the real provider_id via GET /users/{ACw}?account_id=SENDER_ID before invite/messaging.

The ACw→ACo char-swap (index 2 w→o) is unreliable; raw ACw returns a misleading

403 feature_not_subscribed. (Opcom historically used the char-swap for /chats, but the GET-resolve

is the safe rule.)

  • cannot_resend_yet = with-note weekly cap (with-note unavailable on some accounts) AND an account-wide

burst cap (~25/day → multi-day lock). On those accounts send invites WITHOUT a note; personalize via DM

after they accept.

  • Rate limits: LinkedIn caps ~80-100 invites/day/account; failed requests still count. On 429, stop for

the day and wait 2-3 hrs minimum. disconnected_account = Unipile session expired → refresh cookies in

the Unipile dashboard.

Reactions / boost rules

  • Boost reactions are a CONTEXTUAL MIXED-TYPE set (like / insightful / support / celebrate / love), never

all-like. ~15 per post. Comment rotation: never repeat the same profile day-to-day; Robert + Branko

comments/post. Engine: saif_boost.py, pool Clients/_ops/local_commenter_pool.py.

  • Every comment must also fire a like from the same account (comment alone reads transactional).
